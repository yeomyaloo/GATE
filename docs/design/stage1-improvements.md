# 설계안: 1단계(① gate-pkg) 알려진 한계 보완

- 상태: **승인 (2026-11-19)**. 6장 결정 4개 모두 추천안으로 확정
- 대상: 1단계 진행 기록의 "알려진 한계" 중 남은 4개 (3번은 해결됨)

## 1. 한계 1: npm 버전 범위를 풀지 않는다

**지금:** `^4.21.2`, `~1.2`, `>=2 <3` 같은 범위는 최신판 기준으로 검사하고 메모만 남긴다. `package.json`은 대부분 범위로 적으므로, PR 검사(`gate-pkg diff`)에서는 실제로 설치될 버전과 다른 버전을 검사하게 된다.
- 예: `"express": "^4.21.2"`를 검사하는데 최신판이 5.x라면, 5.x의 설치 스크립트·게시자·공개일을 보게 된다

**바꿀 것:** npm이 고르는 버전을 똑같이 고른다.
- 지원할 문법: `^`, `~`, `x`·`*` 범위, `1.2 - 2.3` 하이픈 범위, `>= <= > < =` 비교, `||`
- 사전 배포판(`-beta` 등)은 npm 규칙대로 범위에 사전 배포판이 적힌 경우에만 고른다
- 고르는 순서도 npm과 같다: `latest` 태그가 범위에 맞으면 그것, 아니면 범위에 맞는 가장 높은 버전
- 범위에 맞는 버전이 없으면 "검사 불가"(`PKG-UNCHECKED`)로 둔다. 통과로 처리하지 않는다
- 해석하지 못한 문법(git·파일·URL 등)은 지금처럼 메모와 함께 둔다
- **PyPI**(결정 2): `>=2.0,<3`, `~=2.1`, `==2.*`, `!=` 같은 PEP 440 지정자도 같은 방식으로 푼다
- 테스트: npm 공식 문서 예시와 node-semver 테스트 사례 일부를 옮겨 쓰지 않고 다시 작성한다. 실제 레지스트리 응답(녹화본)으로 express·react 범위를 확인한다

## 2. 한계 2: npm 다운로드 API 요청 제한

**지금:** 패키지마다 다운로드 수를 따로 묻는다. 의존성이 수십 개 추가된 PR이나 측정에서 할당량을 넘으면 "검사 불가"가 늘어난다(측정 중 실제로 npm 181개가 다운로드 수를 받지 못함).

**바꿀 것:**
- 묶음 조회 API `api.npmjs.org/downloads/point/last-week/a,b,c`로 한 번에 최대 128개를 묻는다(확인: 응답 200)
- 스코프 패키지(`@scope/name`)는 묶음 조회가 되지 않으므로 지금처럼 하나씩 묻는다
- 결과는 지금 쓰는 파일 캐시에 패키지별로 나눠 저장한다(다음 실행에서는 묻지 않음)
- 429 응답이면 `Retry-After`를 지키고, 그래도 안 되면 지금처럼 "검사 불가"로 표시한다

## 3. 한계 4: 탐지율을 재지 않았다

**지금:** 오탐률(정상 600개 중 차단 0)만 쟀다. 진짜 악성 패키지를 얼마나 잡는지는 확인된 사례 몇 개뿐이다.

**바꿀 것:** OSV의 악성 패키지 목록(`MAL-` 항목, 원자료는 OpenSSF malicious-packages, Apache-2.0)으로 잰다.

**먼저 알아 둘 점: 그대로 재면 결과가 의미 없다.**
- gate-pkg는 OSV를 조회하므로, OSV에 올라간 악성 패키지는 당연히 100% 잡는다(`PKG-VULN`)
- npm은 악성 패키지를 지운 뒤 `0.0.1-security`라는 빈 자리표시 버전으로 바꾼다. 그래서 지금은 레지스트리에서 원래 메타데이터(설치 스크립트, 게시일)를 볼 수 없다

**그래서 두 가지를 따로 잰다.**

| 지표 | 방법 | 의미 |
|---|---|---|
| ① 이름만으로 잡는 비율 | 악성 패키지 이름을 `TypoDetector`(인기 목록 대비 철자 흉내)에 오프라인으로 넣는다. OSV·레지스트리 조회 없음 | **OSV에 올라가기 전(0일)**에도 잡을 수 있는 비율. 철자 흉내가 아닌 악성 패키지(의존성 혼동 등)는 원래 못 잡는다 |
| ② OSV 반영 후 | 같은 표본을 실제 `gate-pkg check`로 (`PKG-VULN`·`PKG-EXIST`) | 확인용. 거의 100%가 정상 |

- 표본: npm·PyPI 각 300개 무작위(시드 고정). 이름 목록과 OSV ID만 저장소에 남긴다(출처·라이선스 표기)
- 함께 기록: 놓친 이름의 유형(의존성 혼동, 무작위 이름, 스코프 사칭 등)
- **데이터 내려받기가 필요하다**(결정 3): OSV 전체 묶음 npm 약 **222MB**, PyPI 약 **38MB**. 작업 폴더(저장소 밖)에 받아 MAL 항목만 골라낸 뒤 지운다

## 4. 한계 5: `npx`(받아서 바로 실행)는 검사하지 않는다

**지금:** 설치 명령(`npm install`, `pip install` 등)만 본다. AI 도구는 MCP 서버를 띄울 때 `npx -y some-mcp-server`를 자주 쓰는데, 이건 **설치와 실행을 한 번에** 해서 더 위험하다.
- 훅 래퍼의 빠른 통과 조건에 `npx`·`uvx`가 없어서 JVM을 켜지도 않는다

**바꿀 것:**
- 명령 해석 추가:

  | 명령 | 검사할 패키지 |
  |---|---|
  | `npx [-y] pkg[@ver]`, `npx -p pkg cmd` | pkg |
  | `npm exec pkg`, `npm x pkg` | pkg |
  | `pnpm dlx pkg`, `yarn dlx pkg` | pkg |
  | `uvx pkg`, `uv tool run pkg`, `uv tool install pkg` | pkg |
  | `pipx run pkg`, `pipx install pkg` | pkg |

  - `npx --package=a -- b`처럼 실제 패키지와 실행 이름이 다른 경우도 처리한다
- 훅 래퍼의 빠른 통과 조건에 `npx`·`uvx`·`pipx`·`dlx`·`exec`를 추가한다
- **MCP 설정 검사**(결정 4): PR에서 `.mcp.json`·`.claude/settings.json`·`claude_desktop_config.json`의 `mcpServers.*.command`/`args`가 `npx`·`uvx`로 새 패키지를 띄우면 그 패키지를 검사한다
  - AI 코딩 도구 연동이라는 이 프로젝트의 차별점에 정확히 맞는다
